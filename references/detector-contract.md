# 检测器契约

棘轮契约（`contract.md`）规定发现如何与基线比较；本文件规定检测器满足哪些条件，它输出的发现才可信。

## 1. 确定性（Deterministic）

相同的源码、配置和检测器版本，必须得到相同的 `findings`、`hard`、`advisory` 和覆盖结果，输出顺序也相同。

不依赖文件系统的遍历顺序、当前时间、随机数、绝对路径或机器相关的临时路径。先按仓库相对路径给文件排序，再按 key 给发现和诊断排序；并行处理时，报告顺序不能取决于任务完成的先后。

## 2. 失败关闭（Fail closed）

以下情况都判失败，不能报成「0 个发现」：

- 源码解析失败。
- 必需的配置无法读取。
- 必需的依赖图无法构建。
- 确定性的仓内引用无法解析。
- 检测器异常退出，或返回的结果明显不完整。

无法证明扫描有效时就失败，也不用这次结果更新基线。

## 3. 覆盖可核对（Coverage-aware）

每个检测器都报告：计划扫描多少、实际成功扫描多少、哪些内容无法处理。指标按检测器的职责选，不要求共用一套字段，也不要新增统一的汇报模块。

| 检测器 | 覆盖指标 |
|---|---|
| 复杂度 | `source_files`、`parsed_files`、`functions`、`parse_failures` |
| 依赖图 | `source_files`、`parsed_files`、`modules`、`resolved_edges`、`unresolved_static_imports` |
| 测试形态 | `test_files`、`parsed_files`、`test_cases` |
| 死代码 | `source_files`、`modules`、`import_edges` |

通过的最低条件：
- 计划扫描数大于 0。
- 所有计划内文件都解析成功。
- 关键实体数不低于该检测器的下限。下限按当前仓库的实际数量设定：正常增删代码不会触发，扫描范围意外丢掉一大块时一定触发。
- 确定性的未解析输入列在健康检查结果里，不从依赖图中静默消失。静态分析本来无法确定的动态表达式可以作为已说明的限制。

计数方式：
- 文件类检测器在解析前统计范围内的文件数，只把解析成功的文件计入 `parsed`。
- 图类检测器分别统计已解析文件、建成的模块、已解析的边和未解析的确定性引用。
- 既按文件扫描、又对函数数设下限的检测器，摘要同时报告这两个数。

比较发现之前和更新基线之前，都执行同样的健康检查。用户要求更新基线，不是接受无效扫描的理由。

通过时的摘要要写出扫描量，例如「73 个文件 / 1540 个函数」或「83 个模块 / 241 条静态依赖边」。

## 4. key 稳定（Stable identity）

以下无关改动不能改变已有的 key：
- 插入无关代码行；
- 格式化；
- 在其他函数之前新增一个无关函数。

key 的组成：
- 仓库相对路径（统一用 `/` 分隔）加符号名，或规范化内容的哈希。
- 不用行号、列号、全文件统一编号的匿名函数序号、临时绝对路径。
- key 标识受影响的实体或依赖关系，不标识解析器碰巧遇到它的位置。
- 同一文件内确实同名的局部实体（匿名函数、重载），按出现顺序加 `~2`、`~3`。别处新增实体不能让已有 key 重新编号。

同一个问题只报一次：
- 大的重复片段已经包含小片段时，不再报小片段。
- 模块之间的依赖关系按模块对报一次，不因为多处 import 而重复出现。

## 5. 不静默跳过（No silent unknowns）

检测器遇到无法处理的确定性代码结构时，要么判失败，要么把它列进健康检查结果的 unsupported 项，不能直接忽略。

必须进入健康检查的例子：
- 字面量 `import("./known-file.js")` 解析不到目标文件。
- 合法源码无法被指定的解析器解析。
- 仓库相对路径的解析逻辑出错。

可以作为已说明限制保留的例子：
- `import(variable)` 这类变量式动态路径。
- 反射。
- 运行时依赖注入容器。

仓库的路径别名和框架加载约定，要写明是否已解析。

## 6. 夹具证明（Fixture-proven）

用夹具分别证明检测器正确性和棘轮正确性。

检测器正确性：
- 正例：真实违规能被发现。
- 反例：明确合法的代码不误报。
- 边界：数值门槛测门槛值和刚超过门槛的值；依赖图测允许边和禁止边；扫描范围测关键的纳入项和排除项。
- key 稳定：插入无关行或新增无关模块后，已有 key 不变。
- 解析失败：扫描范围内有无法解析的文件时失败。
- 覆盖失败：空扫描或覆盖明显不完整时失败。

棘轮正确性：
- 当前发现与基线一致：通过。
- 新增发现：失败。
- 违规改善或消失但基线未收紧：以虚挂失败。

硬规则不需要与基线相关的用例。多个行为可以合进少量测试，不要求固定的测试函数数量。使用成熟外部工具时，不重测它的内部算法，只测输出转换、key 归一化、覆盖检查、失败传播，以及与棘轮的衔接。

## 7. 扫描范围正确（Scope correctness）

写明：
- 扫描哪些目录，明确排除哪些目录。
- 正式代码与测试如何区分，测试是否由单独的检测器扫描。
- 生成代码按目录还是按命名约定排除。
- 第三方或 vendored 代码如何识别。
- 仓库路径别名和框架约定是否已解析；没覆盖的，限制是什么。

`node_modules`、`vendor`、构建产物、覆盖率产物和生成代码不计入源码指标。排除规则与仓库已有检查保持一致。扫描范围写成集中、易读的常量；代码目录或命名约定变了，重新核对范围。
