## 1. 圈复杂度

- **目的**：防止函数一点点变复杂。
- **信号**：每个函数 1 + 分支数（if、循环、catch、三元、case、`&&`/`||`/`??`）。近似算法即可，它只和自己的历史比，不需要与专业工具一致。
- **搬家不降分**：把判断剪到旁边的私有函数再调用一次，调用方的分数不变，不能靠搬家达标。计分规则：
  - 定义在调用方外面、同一文件内、未导出、且只被一处直接调用（`name(...)`）的函数：它的判断数加到调用方分数上，它自己也照常单独计分。加回时不从调用方原有分数里扣。
  - 被两处及以上调用，或导出给别的文件的函数：不加回调用方。
  - `obj.name()`、作为回调传参：不算直接调用。
  - 函数内部的匿名回调和内层函数：判断一律算在外层函数里。
- **规则**：数值型基线规则，门槛默认 30。
- **key**：`路径#函数名`，匿名函数用赋值目标或属性名；都没有时写成「外层函数名>调用名」（例如 `matchEntries>filter`、顶层的写 `(顶层)>post`），同名加 `~n`。不要用全文件统一编号的 `(匿名)~n`：前面多一个匿名函数，后面所有 key 都会错位。被加回调用方的函数仍按自己的分数出现在基线里。
- **失败提示**：不要写「拆成几个有名字的步骤」。写成：这次改动若把两件不同的事写进了同一个函数，把那件新事挪出去；只为降分搬代码不会通过。
- **误报**：分派表式的大 switch、协议对齐代码是固有复杂度——允许进基线，提交里写理由。
- **扫描下限**：对函数总数设下限（设法见 `detector-contract.md` 第 3 节），防止遍历坏掉后空转通过。
- **提示级（可选）**：复杂度达到门槛八成（默认 25 以上）的函数，提前提醒。提醒文案与失败提示的要求相同。

## 2. 体量

- **目的**：控制「读懂一个文件要装进脑子/上下文的量」。
- **信号**：文件 token 数或行数、最大函数行数、文件内函数+类数量、文件的仓内依赖数；文档的长度和最大章节长度。
- **定义数只数有名字的函数和类**：内联回调 `(x) => …` 不是可独立导航的定义。按所有函数节点计数时，抽出几个小函数、把循环改成 `map` 都会让数字暴涨，文件反而更短。
- **测试文件的最大函数**：`test` / `it` / `describe` / `before*` / `after*` 的回调是用例容器，不算函数；否则整个 `describe` 块就是「最大函数」，加几个用例就超标。
- **规则**：数值型，分 warning / hard 两档。新文件超过 hard 档即失败；历史超标文件相对基线明显增长才失败，例如同时超过一个绝对增量和 20% 的比例。
- **默认**：文件 16000 token、函数 300 行、定义 50 个、依赖 20 个（hard 档）。
- **误报**：生成代码、数据表文件——排除出扫描范围而不是进基线。
- **改指标定义时的基线迁移**：不要整体重建（体量守卫通常没有虚挂检查，旧基线可能落后很久，重建会把这段时间的增长全部认下）。只重算定义变了的指标，取旧值与新值中较小者；旧定义计数更宽时，旧值是新定义下历史值的上界，当前值超过它就是确定的增长。

## 3. 测试形态

只读测试源码，不运行测试、不读耗时。

| 规则 | 类型 | 说明 |
|---|---|---|
| 测试体没有断言 | 硬 | 断言包括断言库调用、`expect(`、测试上下文的 `plan`/`assert`。hook（before/after）和 skip/todo 不算测试体 |
| 提交了 focus（`.only`、`fit`、`fdescribe`、`{ only: true }`） | 硬 | 会让同文件其余测试悄悄不跑 |
| 结果写死的断言（`assert.ok(true)`、`expect(1).toBe(1)`、`assertTrue(True)`） | 硬 | 形同虚设 |
| 非端到端测试里长的固定等待（`sleep`/`setTimeout` 字面量 > 50ms、`waitForTimeout`） | 硬 | 慢且不稳；改成轮询条件 |
| 浏览器/端到端依赖只能出现在端到端目录；默认测试命令不能扫到该目录 | 硬 | 保证单元测试快且不需要浏览器 |
| 单个测试文件里起服务/建库/启浏览器超过 1 次 | 计数型基线 | 共用一次启动。`server.listen` 后在声明 `server` 的同一函数里又 `server.close` 的是探测空闲端口，不算 |
| 永久跳过（`skip`、`xit`、`@pytest.mark.skip`、`t.Skip`） | 集合型基线 | key 用 `文件#标题`，不用行号 |

- **误报**：自定义断言辅助函数（例如 `expectValid(x)`）——把仓库的断言辅助名加进识别列表；测试有意多次初始化以验证幂等——用有意保留标记（见 `contract.md`）并写理由。
- **注意**：检查默认测试命令时，要真的展开它的 glob 验证，而不是看字符串里有没有目录名。

## 4. 死代码

- **目的**：找没人用的文件和导出。
- **信号**：建仓内引用图——静态 import/require/export-from、字面量路径的动态导入、框架懒加载的字符串路径。相对路径解析到实际文件（补扩展名、目录补 index）。
- **规则**：两条集合型基线规则：无引用文件；有引用的文件里没人用的导出。
- **入口（不报）**：程序入口、HTML 引用的脚本、包清单的 main/bin/scripts 里出现的文件、测试文件本身、按目录加载的插件目录、工具按文件名加载的配置（`*.config.js`、`conftest.py`、`setup.py` 等）。
- **测试里的引用算在用**：否则只被测试覆盖的公共函数会被误报。
- **动态加载的模块对象按成员算**：`import()` / 测试辅助加载到的模块对象，不要一律当成「全部导出都用到」——测试最常这样加载，一个 `const { a } = await load('x')` 就会让 x 的所有导出都显得在用，把真死代码藏起来。按用法确定取用的导出：解构的键、`mod.a`、`mod['a']`；表驱动测试里 `mod[suite.createName]` 取本文件对象字面量中所有 `createName: '…'` 属性值，`load(suite.path)` 同理认 `path` 属性值。模块对象被传给函数、展开或下标认不出时，才退回「全部用到」。需要单独找「只被测试引用」的代码时，另设一条规则。
- **不要猜**：`import(变量)`、反射、依赖注入容器——解析不到就不算引用，让它进基线，并在汇报里说明误报来源。例外：`import()` 的参数是表达式、但其中有形如仓库根相对路径的字符串字面量（`import(pathToFileURL(path.resolve(ROOT, 'backend/x.js')).href)`），这是确定的，算引用。
- **入口要显式声明**，不要让它们长期留在基线里，否则真正的死代码会被淹没：
  - 按路径字符串加载的文件（Electron 的 preload）、供复制的模板和示例、对外约定的统一出口（组件库 barrel、功能模块唯一接入点、插件包入口）：写成守卫里的常量清单，注明加载方式或约定来源。
  - 按拼出来的名字绑定的处理函数（CLI 命令表里的 `f"flow_{name}"`、`getattr(mod, f"cmd_{x}")`）：按「模块 → 名字」列进清单，注明拼名位置。
  - 清单要反向对账：列了但已不是该模块导出的名字，判失败，防止清单过时。
  - 仓库有固定的字符串加载约定时（如测试辅助 `freshImport('路径')`），加进识别列表。
  - 做完以上几步，死代码基线里仍然大多是变量式动态加载造成的误报时，把「所在模块被变量式动态加载的导出」降为提示级。
- **误报**：公共库对外导出的 API（整个包都是入口）；被外部系统按名字调用的函数。

## 5. 重复代码

- **目的**：防止新的复制粘贴。
- **信号**：同一语句列表里连续的可执行语句的 token 序列；比较前抹掉标识符名字（改名后的复制也算）、忽略空白和注释；字面量、关键字、运算符保留。
- **简单调用串**：片段里每条语句都只是用现成的值调用一次函数（setter、选择器、hook 取值、路由注册）时，抹掉名字后只剩调用形状，彼此必然相同；这种片段要求保留名字后也逐字相同才报，否则一串给不同字段赋值的 setter 会被当成复制。片段里只要有一条带逻辑的语句（条件、循环、赋值、嵌套调用、带块体的回调），仍按抹掉名字的规则比较。
- **规则**：计数型基线规则，key 为规范化 token 序列的哈希，count 为出现处数；同一文件内复制也算。
- **门槛**：默认 40 token；被更大重复片段包住的小片段不重复报。
- **排除**：测试、生成代码、import 区块。
- **误报**：结构相同但语义不同的样板（例如一组平行的 CRUD 函数）——进基线；若团队认定是有意的平行实现，更新基线时写理由。
- **必须逐字一致的镜像**（前后端各一份的同一算法、冻结不改的已上线迁移）：用有意保留标记标在其中一侧。被标记的那处出现不再计入，剩下不足两处的组不报；同一文件内的其余重复照报。

## 6. 运行形态

只看代码形状，不做复杂度标注、不测耗时。

### Effect propagation

把昂贵操作建模为 effect：函数直接执行某种 effect，或调用一个已知带该 effect 的函数，它就具有该 effect。跨函数、跨文件时沿调用和导入关系传播，直到结果不再变化。定义了 `db-read`、`db-write`、`network` 三种；JavaScript 参考实现只识别数据库读写，不要求识别 HTTP 客户端。

N+1 是 `db-read` / `db-write` 出现在重复执行上下文里的情形。查询层函数要有证据表明它确实访问数据库，不能因为文件在 query 目录里就算有 effect。

| 规则 | 类型 | 说明 |
|---|---|---|
| 循环里逐项查询（N+1） | 集合型基线 | 在循环体或 `map`/`filter`/列表推导等逐项回调里：调用 `prepare`/`execute`、调用 prepared statement 的 `get`/`all`/`run`、**调用从查询层导入、且确实访问数据库的函数**、ORM 的逐项 `find`/`get`。key 为 `路径#函数#被调名` |
| 三层循环且最内层引用外层循环变量 | 硬 | 两层不报；只引用自身变量的三层循环（例如固定次数的内循环）不报 |
| 业务层 SQL 的 SELECT 没有 WHERE 也没有 LIMIT | 集合型基线 | 只在路由/服务等业务层查；排除查询层，以及导入导出这类有意全量读取的模块 |

- **「循环里」只指循环体和逐项回调**：循环头的取数来源只求值一次，不算——`for x in query()` 的 `query()`、`query().map(fn)` 的接收者、推导式第一个 `for` 的来源。推导式第二个起的 `for` 来源、`while` 的条件会逐轮重算，照算。按「往上找到循环节点就算」实现最容易把这类一次性查询误报成 N+1，自研检测器要沿着父链记下是从循环的哪个字段进来的。
- **最容易漏的**：只识别「同文件里 prepare 出来的语句」会漏掉业务层调用查询层函数的 N+1，而那才是大头。要按 import 来源识别查询层函数。
- **查询层函数要确认真的访问数据库**：查询目录里也会有纯函数（取值规整、参数校验）。对查询目录的每个导出做一次文件内 + 跨文件的不动点分析：直接用到数据库连接、调用 `prepare`/`exec`/`transaction`，或调用了会访问数据库的函数，才算查询；认不出形状的导出（工厂调用结果等）保守地算查询。「认不出就保守」只用于查询层内部；查询函数调用了查询层以外的普通模块（取整、解析、日期换算），那个模块不访问数据库，不能因为「不在已扫描的查询模块里」就算成查询，否则一个纯计算的依赖会把整条调用链都染成查询。
- **事务内批量写不报**：在事务回调里对循环外预编译好的语句逐条 `run`，是 better-sqlite3 这类同步驱动推荐的批量写法。所在函数若在本文件里只从事务回调中被调用（且未导出），同样算在事务里。事务里逐条读（`get`/`all`）照报。
- **误报**：迁移脚本、一次性导入里有意逐条写入、循环次数有固定小上限的——用有意保留标记写明理由，而不是留在基线里。

## 7. 循环依赖

- **目的**：模块之间不许在加载期互相引用成环。
- **信号**：只取加载期的边（静态 import、require、export-from）；运行时才加载的 `import()`、函数内的延迟 import 不算。用 Tarjan 求强连通分量，成员数 > 1 即环。
- **规则**：现状为 0 时做硬规则；存量多时做集合型基线规则，key 为排序后的成员列表。
- **边要落到真正依赖的模块**：Python 的 `from pkg import sub` 在 `sub` 是子模块时，边只连到 `pkg.sub`，不要再连一条到 `pkg`（`__init__`）——加载子模块不依赖包入口里定义的名字。多连这条边，每个「包入口再导出子模块、子模块又 `from . import 兄弟`」的包都会被报成环。导入的名字不是子模块（包入口里定义的函数、常量）时，照旧连到包；`import *` 也连到包。
- **跳过**：语言本身禁止循环依赖时（Go 的包导入）。

## 8. 架构边界

架构规则复用静态 import 依赖图，用 `源路径 → 目标路径` 判断依赖方向是否被禁止。只在仓库已有可验证的目录或模块边界时启用。现状为 0 处时做硬规则；有合理存量时按模块对记入基线。

### 8.1 Forbidden dependency

含义是 A 不允许依赖 B，例如 `domain → infrastructure`、`frontend → database`、`route → query`、`feature-a → feature-b/internal`。按 `from` 路径和目标路径匹配依赖边；key 用 `源模块 → 目标模块`，同一模块对只报一次，不用行号。

### 8.2 Allowed dependencies

某个架构区域只允许依赖列出的区域，例如 `domain` 只能依赖 `domain` 与 `shared`。只在仓库已有清晰分区时配置；不要要求每个项目都建立区域表。

### 8.3 Required path

表达简单的架构意图，例如 route 必须经过 service 才能使用 query。静态规则只实现 `route → query` 禁止，不做数据流或多跳路径分析。

### 8.4 Module encapsulation

仅在仓库已有明确模块入口约定时启用。

- `cross-module-deep-import`：跨模块只许导入模块公开入口；例如 `features/order → features/user/index.js`，不许直接导入 `features/user/src/view.js`。
- `internal-api-import`：按仓库约定禁止跨模块访问 `internal/`、`private/` 等明确私有目录。公开入口位置和私有路径必须来自实际目录约定。

不得仅凭文件名猜完整模块边界。可以允许 `features/order → features/user` 或 `features/user/index.js`，同时禁止 `features/user/internal/cache.js`。key 仍是稳定的模块对。

### 8.5 Containment

边界定义足够完整时，可检查正式业务模块是否都属于某个已声明区域；遗漏时报告 `architecture-unclassified`。默认不启用，避免把工具、示例或特殊目录误判成业务模块。它用于发现通过新增 `misc/`、`temp-core/` 一类目录绕开现有边界的情况。

## 9. 其他可选守卫

- **注释残留**：注释里的 TODO/FIXME/HACK、描述修改历史的词（「之前」「改为」「兼容旧版」「临时」、legacy、deprecated）。计数型基线，key 为文件。关键词表要先人工过一遍，业务含义的「之前」会误报。

## 不建议做成守卫的

- 同名导出跨文件：分层架构里各层用同名函数逐层转发很常见，噪音大。
- 命名风格、一词一义、可推导状态：需要语义判断，静态规则误报高，留给代码审查。
- 循环里的 `await`：很多是有意顺序执行，逐个判断成本高于收益。
