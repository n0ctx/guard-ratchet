# 棘轮契约

所有守卫共享的比对语义。检测器可以千差万别，这部分必须一致——它决定了「只许变好」是否真的成立。`scripts/ratchet.py` 是参考实现，`conformance/cases.json` 是可执行的规格。

## 概念

- **发现（finding）**：`{rule, key, count}`。
  - `rule`：规则名，例如 `fn-complexity`、`loop-query`、`dead-export`。一个守卫可以有多条规则。
  - `key`：稳定的位置标识，例如 `src/a.py#parse`、`src/db.py#load#get_user`、重复片段的内容指纹。
  - `count`：非负整数。集合型规则（有或没有）用 1；计数型（某文件里出现几次）用次数；数值型（复杂度）用数值本身。
- **基线（baseline）**：上次确认的发现快照 `{version, guard, entries: {rule: {key: count}}}`，提交进仓库。
- **硬规则违规（hard）**：不进基线，出现即失败。
- **提示（advisory）**：可选。只打印，不进基线，不影响判定。用于接近门槛的提前提醒、或检测本身不确定的信号；不要用它替代本该失败的规则。

## 判定

一次检查失败，当且仅当以下任一成立：

| 情况 | 定义 | 为什么失败 |
|---|---|---|
| 扫描不可信 | 有文件解析失败，或扫描数低于下限 | 否则「扫不到」会被当成「没问题」 |
| 硬规则违规 | `hard` 非空 | 这些问题不允许以任何理由存量化 |
| 新增 | 当前有、基线没有的 `rule:key` | 新问题 |
| 变差 | 当前 count > 基线 count | 旧问题更严重了 |
| 虚挂 | 当前 count < 基线 count（含消失） | 基线必须跟着改善收紧，否则留出的余量会被悄悄用掉 |

虚挂也算失败这一点容易被省略，但它是棘轮能「只降不升」的原因：如果某函数复杂度从 45 降到 20 而基线仍写 45，之后再涨回 44 也不会被发现。

## 更新基线

- `--update-baseline`（或参考实现的 `update` 子命令）用当前发现整体重写基线：按 rule、key 排序，同一 rule+key 累加，丢弃 count 为 0 的条目。
- 扫描不可信时拒绝写基线，退出 1。
- 硬规则违规不写进基线；写完基线后仍以退出 1 提示这些违规要修。
- 基线的每次变化都应出现在提交里，并在提交说明里写理由（「修好了 X」或「有意保留 Y，因为……」）。

## 数值型规则的门槛

数值型规则（复杂度、文件体量）只在超过门槛时才产生发现。例如复杂度门槛 30：复杂度 25 的函数不产生发现；45 的函数产生 `count=45` 的发现，之后降到 31 就是虚挂（要把基线改成 31），降到 30 以下发现消失，同样是虚挂（要删掉条目）。

计数型规则同理：例如「每个测试文件最多启动一次服务」，只有次数大于 1 的文件产生发现。

## key 设计

- 用「相对路径 + 符号名」或规范化内容的哈希，不要用行号或列号。
- 同一文件内同名的情况（匿名函数、重载），按出现顺序加 `~2`、`~3`。
- 路径统一用 `/` 分隔、相对仓库根。
- 同一个问题只报一次：例如大的重复片段已经包含小片段时，不要把小片段也报出来。

## 命令行约定

每个守卫对外表现一致，方便接入和测试：

- 默认：检查，打印结果
- `--update-baseline`：重写基线
- `--baseline <path>`：基线路径，默认在仓库内固定位置
- `--root <dir>`：扫描的根目录，供夹具测试指向临时仓库
- 退出码：0 通过；1 未通过；2 参数或输入错误
- 失败信息按类别分组，每条给出 key、当前值与基线值，并提示下一步（修掉、或者更新基线并写理由）

## 检测器输出格式（使用参考实现时）

```json
{
  "guard": "complexity",
  "scanned": 640,
  "min_scanned": 100,
  "parse_failures": [],
  "hard": ["tests/a_test.py:3 提交了 .only"],
  "advisory": ["src/b.py#load 复杂度 26，接近门槛 30"],
  "findings": [
    {"rule": "fn-complexity", "key": "src/a.py#parse", "count": 41, "detail": "可选的说明"}
  ]
}
```

常见接法：检测器脚本打印这段 JSON，由 `python3 ratchet.py check --findings - --baseline guards/complexity.json` 读 stdin 比对；更新时换成 `update`。也可以在检测器里直接实现同样的比对逻辑（例如仓库没有 Python），前提是通过全部一致性用例。
