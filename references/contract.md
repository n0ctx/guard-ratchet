# 棘轮契约

所有守卫共用的比对语义。检测器可以各不相同，这部分必须一致，它决定「只许变好」是否真的成立。`scripts/ratchet.py` 是参考实现，`conformance/cases.json` 是可执行的规格。检测器如何证明自己的扫描可信，见 `detector-contract.md`。

## 概念

- **发现（finding）**：`{rule, key, count}`。
  - `rule`：规则名，例如 `fn-complexity`、`loop-query`、`dead-export`。一个守卫可以有多条规则。
  - `key`：稳定的位置标识，例如 `src/a.py#parse`、`src/db.py#load#get_user`、重复片段的内容指纹。设计要求见 `detector-contract.md` 第 4 节。
  - `count`：非负整数。集合型规则（有或没有）用 1；计数型（某文件里出现几次）用次数；数值型（复杂度）用数值本身。
- **基线（baseline）**：上次确认的发现快照 `{version, guard, entries: {rule: {key: count}}}`，提交进仓库。
- **硬规则违规（hard）**：不进基线，出现即失败。
- **提示（advisory）**：可选。只打印，不进基线，不影响判定。只用于接近门槛的提前提醒，或检测本身不确定的信号；本该失败的规则不能改成提示。

## 判定

以下任一情况成立，检查失败；都不成立，检查通过。

| 情况 | 定义 | 为什么失败 |
|---|---|---|
| 扫描不可信 | 有文件解析失败，或扫描数低于下限 | 否则「扫不到」会被当成「没问题」 |
| 硬规则违规 | `hard` 非空 | 这些问题不允许以任何理由存量化 |
| 新增 | 当前有、基线没有的 `rule:key` | 新问题 |
| 变差 | 当前 count > 基线 count | 旧问题更严重了 |
| 虚挂 | 当前 count < 基线 count（含消失） | 基线必须跟着改善收紧，否则留出的余量会被悄悄用掉 |

虚挂判失败最容易被省略，但它是棘轮只降不升的原因：某函数复杂度从 45 降到 20 而基线仍写 45，之后涨回 44 也不会被发现。

## 数值型和计数型规则的门槛

数值型规则（复杂度、文件体量）只在超过门槛时产生发现。例如复杂度门槛 30：复杂度 25 的函数不产生发现；45 的函数产生 `count=45` 的发现；之后降到 31 是虚挂，要把基线改成 31；降到 30 以下发现消失，也是虚挂，要删掉该条目。

计数型规则同理。例如「每个测试文件最多启动一次服务」，只有次数大于 1 的文件产生发现。

## 更新基线

- `--update-baseline`（参考实现里是 `update` 子命令）用当前发现整体重写基线：按 rule、key 排序，同一 rule+key 累加，丢弃 count 为 0 的条目。
- 扫描不可信时拒绝写基线，退出 1。
- 硬规则违规不写进基线；基线写完后仍以退出 1 结束，提示这些违规要修。
- 基线的每次变化都随代码一起提交，提交说明写明理由：「修好了 X」或「有意保留 Y，因为……」。

## 有意保留标记（可选）

检测器永远分不清、但确实有意为之的写法（前后端必须逐字一致的镜像、一次性迁移、验证幂等的重复初始化），在代码旁边写标记，不留在基线里：

```
// guard-allow(<守卫名>): <理由>
```

- **覆盖范围**：标记单独占一行，覆盖紧随其后的那条语句，以及与它紧挨着、中间没有空行的后续同级语句。要覆盖整个函数，就标在函数声明上。
- **效果**：检测器直接滤掉被覆盖的发现，它们不参与比对，也不进基线。标记跟着代码走，搬位置、改名都不失效；基线条目则在代码挪位置后报一次新增加一次虚挂。
- **失败条件**（检测器作为硬规则违规输出）：没写理由；守卫名不存在；覆盖范围里已经没有该守卫的违规（标记残留）。
- **可审查**：每次运行都把全部标记（位置 + 理由）作为 advisory 列出。
- **使用边界**：先改进检测器；改进后仍分不清的地方才用标记。真问题不能用标记绕过。

使用参考实现时，标记由检测器处理，`ratchet.py` 不感知它：被覆盖的发现不输出，标记问题放进 `hard`，标记清单放进 `advisory`。

## 命令行约定

每个守卫对外表现一致，方便接入和测试：

- 默认：检查并打印结果。
- `--update-baseline`：重写基线。
- `--baseline <path>`：基线路径，默认是仓库内的固定位置。
- `--root <dir>`：扫描的根目录，供夹具测试指向临时仓库。
- 退出码：0 通过；1 未通过；2 参数或输入错误。
- 失败信息按类别分组，每条给出 key、当前值和基线值，并给出下一步：修掉；或运行 `--update-baseline` 并在提交里写理由。

## 检测器输出格式（使用参考实现时）

```json
{
  "guard": "complexity",
  "scanned": 640,
  "min_scanned": 100,
  "parse_failures": [],
  "hard": ["tests/a_test.py:3 提交了 .only"],
  "advisory": ["src/b.py#load 复杂度 26，接近门槛 30"],
  "findings": [
    {"rule": "fn-complexity", "key": "src/a.py#parse", "count": 41, "detail": "可选的说明"}
  ]
}
```

检测器脚本打印这段 JSON，由 `python3 ratchet.py check --findings - --baseline guards/complexity.json` 从 stdin 读入比对；更新基线时把 `check` 换成 `update`。
