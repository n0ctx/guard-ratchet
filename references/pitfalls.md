# 落地时的坑

都是真实落地中遇到过的。每条给出症状和处理办法。

## 基线相关

**基线里用了行号**
症状：一次无关的插行让几十条基线同时「消失 + 新增」。
处理：key 只用路径、符号名、内容哈希。

**基线把别人没提交的改动也记进去了**
症状：另一个会话/同事正在同一分支上改代码，你用工作区生成的基线里含有他们的半成品；他们提交后状态变化，基线立刻虚挂或出现本不该保留的条目。
处理：从干净提交生成——`git archive HEAD | tar -x -C <临时目录>`，把本次自己改动的文件拷进去，再用 `--root <临时目录>` 生成基线，拷回仓库。提交前如果 HEAD 又前进了，重新生成一次。

**别人修好了问题却被守卫拦住**
症状：重构让一段重复消失、一个函数变简单，lint 报「虚挂」。
处理：这是设计如此。在汇报里提醒团队：修好之后运行 `--update-baseline` 把基线一起提交。失败信息里要直接给出这条命令。

**为了让守卫通过去改门槛或业务代码**
处理：门槛按用户给的来，不要调；现有违规就是要进基线。唯一的例外是硬规则当天就有违规——这时修的通常是测试或配置，并且要先和用户确认。

## 扫描范围相关

**扫描空转也算通过**
症状：路径写错或目录改名后，守卫扫到 0 个文件，于是「没有任何问题」。
处理：设扫描数下限；任何文件解析失败都判失败。

**被版本控制忽略、但本地存在的目录**
症状：本地和 CI 上结果不同；在干净检出上死代码守卫报虚挂。
处理：二选一并在汇报里说明——只扫受版本控制的文件（`git ls-files`），或者沿用仓库已有守卫的做法。同一仓库里的守卫要一致。

**跳过规则和已有守卫不一致**
处理：跳过的目录（依赖、构建产物、覆盖率、数据、点开头的目录等）与仓库已有检查保持一致。

## 死代码 / 引用图相关

**约定式加载导致大量误报**
症状：配置文件、按目录加载的插件、测试里用字符串路径加载的模块全被报成死代码。
处理：第一步就把入口和加载约定列清楚。字面量路径的约定（例如 `freshImport('backend/x.js')`）可以识别；变量路径不要猜，进基线并在汇报里说明。

**只被测试引用的代码**
处理：测试里的引用算在用，否则公共函数的单测会让它被误报。

## 测试形态相关

**默认测试命令「看起来」排除了端到端目录，实际没有**
症状：glob 写法被 shell 或测试运行器以不同方式展开。
处理：用一个临时小目录真的跑一次测试运行器（只放几个空测试），确认哪些文件被收集。

**为了验证临时挪走别人的改动**
症状：用 `git stash` / `git checkout --` 暂存同事未提交的改动来跑一次干净的检查，之后再恢复；中途出错或被打断，改动就丢了。
处理：所有「去掉别人的改动」「注入一条违规」的验证都在临时副本里做（`git archive`、`cp -R`、`git worktree add`），工作区从头到尾不动。

**固定等待改成轮询时引入竞态**
处理：先读被测代码，确认轮询的条件在断言依赖的副作用之后才成立（例如「活跃流清空」发生在「消息已落库」之后）。

**自定义断言辅助被判成「没有断言」**
处理：把仓库的断言辅助函数名加进识别列表，而不是放宽规则。

## N+1 相关

**只识别了原始的 prepare/execute**
症状：守卫只抓到查询层内部的循环写入（排序写回、迁移），业务层真正的逐项查询一条没抓到。
处理：按 import 来源识别「来自查询层的函数」，并把 `map`/`filter`/推导式等逐项回调也当作循环体。

## 接入相关

**lint 链本来就是红的**
症状：新守卫接在一个已经失败的步骤后面，永远跑不到。
处理：接入前先跑一次完整链，把已有失败告诉用户；单独运行每个新守卫证明它们本身通过。

**守卫本身没有测试**
症状：守卫逻辑被改坏（例如遍历返回空）却一直显示通过。
处理：每个守卫配三结果夹具测试，并接进 lint。

**守卫太慢**
处理：每个守卫应在几秒内完成；一次解析、多条规则共用，避免重复遍历整个仓库。
