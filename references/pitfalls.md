# 落地时的坑

都是真实落地中遇到过的。每条给出症状和处理办法。

## 基线相关

**基线里用了行号**
症状：一次无关的插行让几十条基线同时「消失 + 新增」。
处理：key 只用路径、符号名、内容哈希。

**基线把别人没提交的改动也记进去了**
症状：另一个会话/同事正在同一分支上改代码，你用工作区生成的基线里含有他们的半成品；他们提交后状态变化，基线立刻虚挂或出现本不该保留的条目。
处理：从干净提交生成——`git archive HEAD | tar -x -C <临时目录>`，把本次自己改动的文件拷进去，再用 `--root <临时目录>` 生成基线，拷回仓库。提交前如果 HEAD 又前进了，重新生成一次。

**别人修好了问题却被守卫拦住**
症状：重构让一段重复消失、一个函数变简单，lint 报「虚挂」。
处理：这是设计如此。在汇报里提醒团队：修好之后运行 `--update-baseline` 把基线一起提交。失败信息里要直接给出这条命令。

**有意保留的写法一搬家就报新增**
症状：把几个有意保留的排序写回合并进一个共用函数，守卫报 2 条新增、8 条虚挂，又要重新写一遍理由；同样的解释在提交说明里反复出现。
处理：先看能不能提升检测精度让它不再被报（例如事务内批量写）。确实只能靠人判断的，用写在代码旁边的有意保留标记（`contract.md`），标记跟着代码走。

**指标定义改了，整体重建基线**
症状：修正了指标的计算方式后直接 `--update-baseline`，没有虚挂检查的守卫（例如体量）顺带把很久以来的增长全部认下，原本该失败的文件变成通过。
处理：只重算定义变了的那几项，取旧值与新值中较小者，其余指标沿用旧基线；汇报里说明哪些失败是因为指标修正而消失的。

**为了让守卫通过去改门槛或业务代码**
处理：门槛按用户给的来，不要调；现有违规就是要进基线。唯一的例外是硬规则当天就有违规——这时修的通常是测试或配置，并且要先和用户确认。

## 扫描范围相关

**扫描空转也算通过**
症状：路径写错或目录改名后，守卫扫到 0 个文件，于是「没有任何问题」。
处理：设扫描数下限；任何文件解析失败都判失败。

**被版本控制忽略、但本地存在的目录**
症状：本地和 CI 上结果不同；在干净检出上死代码守卫报虚挂。
处理：二选一并在汇报里说明——只扫受版本控制的文件（`git ls-files`），或者沿用仓库已有守卫的做法。同一仓库里的守卫要一致。

**跳过规则和已有守卫不一致**
处理：跳过的目录（依赖、构建产物、覆盖率、数据、点开头的目录等）与仓库已有检查保持一致。

**解析时打开了注释或 token，遍历把它们当成语法节点**
症状：为了读标记打开 espree 的 `comment: true`（或查重用的 `tokens: true`），通用的遍历函数顺着 `comments` / `tokens` 数组走进去，注释被当成「这一行开头的节点」，token 的 `type: 'Identifier'` 被当成标识符。
处理：遍历时跳过 `comments`、`tokens` 两个键（以及 `loc`、`range`、`parent`）。所有自带遍历的守卫都要改，不只是公共模块里那一个。

## 死代码 / 引用图相关

**约定式加载导致大量误报**
症状：配置文件、按目录加载的插件、测试里用字符串路径加载的模块全被报成死代码。
处理：第一步就把入口和加载约定列清楚。字面量路径的约定（例如 `freshImport('backend/x.js')`）可以识别；变量路径不要猜，进基线并在汇报里说明。

**动态加载的模块对象被当成「全部导出都用到」**
症状：测试里 `const { upsert } = await freshImport('x.js')` 或 `const mod = await freshImport(suite.path); mod[suite.getName]`，守卫把 x.js 的全部导出都记为在用，没人调用的查询躲过检查；改成按成员算后，一次冒出二十多条真死代码。
处理：按解构键、点号、字符串下标，以及对象字面量里同名属性的字符串值确定用到的导出（见 `guard-catalog.md` 第 4 节）；只有模块对象逃逸时才退回全部。

**只被测试引用的代码**
处理：测试里的引用算在用，否则公共函数的单测会让它被误报。

## 测试形态相关

**默认测试命令「看起来」排除了端到端目录，实际没有**
症状：glob 写法被 shell 或测试运行器以不同方式展开。
处理：用一个临时小目录真的跑一次测试运行器（只放几个空测试），确认哪些文件被收集。

**为了验证临时挪走别人的改动**
症状：用 `git stash` / `git checkout --` 暂存同事未提交的改动来跑一次干净的检查，之后再恢复；中途出错或被打断，改动就丢了。
处理：所有「去掉别人的改动」「注入一条违规」的验证都在临时副本里做（`git archive`、`cp -R`、`git worktree add`），工作区从头到尾不动。

**固定等待改成轮询时引入竞态**
处理：先读被测代码，确认轮询的条件在断言依赖的副作用之后才成立（例如「活跃流清空」发生在「消息已落库」之后）。

**自定义断言辅助被判成「没有断言」**
处理：把仓库的断言辅助函数名加进识别列表，而不是放宽规则。

## N+1 相关

**把查询目录里的所有导出都当成查询**
症状：一个只做数字规整的纯函数放在查询目录里，被业务层在循环里调用，报成 N+1。
处理：确认导出真的访问数据库再算（见 `guard-catalog.md` 第 6 节）。

**事务内的批量写被报成 N+1**
症状：排序写回、导入插入这类「事务里复用预编译语句逐条 run」的代码占了运行形态基线的一半，真正的逐项查询被淹没。
处理：事务内对预编译语句的逐条写入不报，逐条读照报。

**只识别了原始的 prepare/execute**
症状：守卫只抓到查询层内部的循环写入（排序写回、迁移），业务层真正的逐项查询一条没抓到。
处理：按 import 来源识别「来自查询层的函数」，并把 `map`/`filter`/推导式等逐项回调也当作循环体。

## 接入相关

**lint 链本来就是红的**
症状：新守卫接在一个已经失败的步骤后面，永远跑不到。
处理：接入前先跑一次完整链，把已有失败告诉用户；单独运行每个新守卫证明它们本身通过。

**只能从 lint 链里跑守卫**
症状：lint 链用 `&&` 串联，前面某一步（包括某个守卫自己）失败，后面的守卫全都跑不到；新会话的 agent 被要求「跑守卫」时不知道该跑哪些命令。
处理：提供一个跑完全部守卫再汇总的统一入口，并写进受版本控制的 agent 说明文件。

**守卫上线后基线和代码一起走样**
症状：其他人或其他 agent 会话在守卫上线后继续大量改代码，没人跑守卫；一段时间后几乎每个守卫都同时报新增和虚挂，分不清哪些是该修的。
处理：说明文件里写明「改完代码跑统一入口」；把统一入口接进 CI 或提交前检查；汇报时提醒用户告知其他正在改代码的人。

**agent 说明文件被 git 忽略**
症状：把守卫用法写进了 `CLAUDE.md`，但它在 `.gitignore` 里，只有本机能看到。
处理：写之前用 `git check-ignore` 确认；被忽略就改写到受版本控制的文件，或告诉用户。

**体量指标把内联回调和测试容器当成函数**
症状：抽出几个小函数、把循环改成 `map`，文件更短了，「定义数」却暴涨；测试文件加三个用例，整个 `describe` 块作为「最大函数」超标。
处理：定义数只数有名字的函数和类；测试文件里 `test`/`describe` 等的回调不算函数。

**圈复杂度 key 按全文件编号匿名函数**
症状：在文件前面加一个箭头函数，后面所有 `(匿名)~n` 的 key 整体后移，基线出现一对「新增 + 虚挂」，数值却没变。
处理：匿名函数写成「外层函数名>调用名」，编号只在同一外层函数内同名时才加。

**守卫本身没有测试**
症状：守卫逻辑被改坏（例如遍历返回空）却一直显示通过。
处理：每个守卫配三结果夹具测试，并接进 lint。

**守卫太慢**
处理：每个守卫应在几秒内完成；一次解析、多条规则共用，避免重复遍历整个仓库。
